### Visual / Functional Defects Found (NOT fixed — report only)
1. **Services dropdown has no overview entry** (`src/components/site/Header.tsx` lines 90–103). On desktop, the "Services" nav button is a dropdown that lists only the 7 individual services (Road & Highway, Thermoplastic, Airport & Runway, Parking, Road Studs & RPMs, Industrial Safety, Line Removal). There is no "All services" / "Services overview" menuitem, so a desktop user cannot reach the `ServicesView` overview (H1 "Commercial marking services") from the top nav — they must click the "Services" CTA on the Home hero, or use the mobile Sheet menu. Recommendation: add a `<DropdownMenuItem onClick={() => go("services")}>All services</DropdownMenuItem>` as the first child of the Services dropdown (mirror what the Saudi Presence dropdown does with its overview menuitem).
2. **LeadPipeline Refresh button click target is occluded by its SVG icon** (`src/components/site/rfq/LeadPipeline.tsx`). The `<RefreshCw>` icon sits inside the `<Button>` such that the button's centroid lands on the SVG, and Playwright/CDP reports `Element is covered by <svg> at its click point`. Clicking the icon does not fire the button onClick. Workaround: click the text "Refresh" portion, or call `btn.click()` via JS. Recommendation: add `pointer-events-none` to the icon (shadcn `Button` already does this in some variants but apparently not consistently here) or restructure so the icon doesn't cover the centroid.
3. **LeadPipeline does not auto-refresh after a successful RFQ submission.** The `RfqForm` and `LeadPipeline` are siblings with no shared parent state. After `POST /api/rfq` returns success, the user sees the "RFQ received" success card, but the pipeline table below still shows the pre-submission counts until the user manually clicks Refresh or reloads the page. Recommendation: lift a `refreshSignal` state up to `ContactRfqView` (or use a small event emitter / `useSyncExternalStore`), or have `RfqForm.submit()` call `LeadPipeline.load()` via a callback prop.
4. **Date input interaction quirk (not a code defect).** Under headless Chromium, `<input type="date">` exposes Month/Day/Year spinbuttons + a "Show date picker" button in the accessibility tree rather than a single textbox. Direct `agent-browser fill` on the spinbuttons was unreliable. Workaround used: invoke the native `HTMLInputElement.prototype.value` setter and dispatch an `input` event so React's controlled component updates. This is purely a tooling/testing note — real users see and interact with the native date picker normally.
